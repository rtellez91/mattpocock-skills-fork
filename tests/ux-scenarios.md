# Behavioral validation scenarios

Run these in fresh agent contexts using the changed skills and realistic source fixtures. Inspect action sequences, evidence, and stopping behavior. This is a manual behavioral protocol, not an automated test or proof of live plugin compatibility. Record the skill version, observed result, and limitations when exercising it.

| Scenario | Expected observable behavior |
| --- | --- |
| Internal rename with no changed behavior | Briefly record design non-applicability; continue engineering without generating a journey or mock |
| Existing accepted component covers the requested UI and all relevant states | Inspect and cite the current contract; assess as covered by existing design; do not require new visual exploration |
| Interview cannot settle ownership across a hosted sign-in boundary | Choose the method that resolves transitions and ownership; preserve the interview; keep inferred user needs distinct from research |
| Unknown navigation could change delivery boundaries | Explain why design must precede a final implementation breakdown; return provisional slices, not automatically ready tickets |
| Stable scope with a bounded missing design decision | Draft a design ticket with decision/evidence criteria; block only deliverables that need its answer; preserve the whole coupled journey |
| Selected desktop image lacks return, error, and narrow-screen decisions | Identify material uncovered scope; do not declare that scope ready merely because an image was selected |
| Product Design plugin unavailable or referenced catalog inaccessible | Name the specific gap; continue independent nonvisual work; do not silently code UI alternatives |
| Visual exploration only, followed by image selection | Record exact selection and evidence; stop without starting implementation unless already authorized |
| Prototype request with an unambiguous selected target | Follow the installed plugin's build and browser QA requirements; return evidence to the question; do not create a production branch automatically |
| Spec contains pending human design choice and an independent complete server task | Dispatch only the eligible implementation task; report the design blocker after independent work; do not poll or invent a decision |
| Closed design issue links obsolete or missing evidence | Inspect the handoff; report pending readiness for affected scope despite the issue state |
| Prototype passes screenshot comparison | Report visual/prototype evidence accurately; retain production interaction and accessibility checks; do not call it user research |

The deterministic installer suite uses temporary directories only. It covers read-only preview, scoped replacement, preservation of unrelated files and lock metadata, repeat/update behavior, refusal of local edits and foreign ownership, unsupported metadata, unsafe paths, staging failure, and retry after metadata failure. It does not modify the current user's installed skills.
